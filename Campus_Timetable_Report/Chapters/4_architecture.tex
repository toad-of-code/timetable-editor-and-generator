This chapter details the structural design of the IIITA Timetabling System. It defines the application topology, the relational database schema, the Excel data ingestion pipeline, the solver's internal data model, and the state-based routing logic used for view management.

%-----------------------------------
\section{Application Topology}

The system architecture consists of three primary components:
\begin{itemize}
    \item \textbf{Frontend (React SPA):} A Single Page Application that handles user interaction, clash detection, and PDF generation. It interacts with the backend through REST API calls.
    \item \textbf{Backend (Supabase):} Provides the API gateway, manages user authentication, and handles database interactions.
    \item \textbf{Database (PostgreSQL):} A relational database that stores institutional data, including users, rooms, subjects, faculty, and the generated timetable slots.
\end{itemize}

%-----------------------------------

\begin{itemize}
    \item \textbf{\texttt{timetables}:} The container for a specific schedule. It stores the iteration name, semester, academic year, and lunch break constraints.
    \item \textbf{\texttt{subjects}:} Contains course metadata, including the course code, credit structure (L-T-P), and elective grouping.
    \item \textbf{\texttt{professors}:} Stores faculty information, uniquely identified by email.
    \item \textbf{\texttt{rooms}:} Physical room data including capacity and room type (Lecture Hall or Laboratory).
    \item \textbf{\texttt{student\_groups}:} Defines student cohorts by program, semester, and section.
\end{itemize}

To support automated generation, the schema includes mapping tables used by the solver engine:
\begin{itemize}
    \item \textbf{\texttt{semester\_clusters}:} Groups subjects by batch, semester, and department to define the scope of a scheduling task.
    \item \textbf{\texttt{cluster\_requirements}:} Maps subjects to clusters, specifying elective groups and estimated enrollment for room allocation constraints.
    \item \textbf{\texttt{professor\_expertise}:} Defines which subjects a professor can teach and their associated preference levels.
\end{itemize}

The system includes a data ingestion module (\texttt{TimetableImporter}) to parse existing Excel-based timetables into the normalized database schema. The process follows a five-step pipeline:

\begin{figure}[htbp]
\centering
\begin{tikzpicture}[
    node distance=1.2cm,
    block/.style={rectangle, draw, fill=gray!10, text width=10cm, align=center, rounded corners, minimum height=0.8cm, font=\sffamily\small},
    arrow/.style={draw, thick, ->, >=stealth}
]

\node[block] (step1) {\textbf{1. Binary Parsing}\\Converts binary \texttt{.xlsx} data to JSON via \texttt{SheetJS}};
\node[block, below=of step1] (step2) {\textbf{2. Header Synchronization}\\Extracts time boundaries and identifies merged cells from header rows};
\node[block, below=of step2] (step3) {\textbf{3. Metadata Extraction}\\Uses Regex to parse course codes, credits, and faculty assignments};
\node[block, below=of step3] (step4) {\textbf{4. Grid Traversal}\\Iterates over grid cells to map days, times, and room locations};
\node[block, below=of step4] (step5) {\textbf{5. Review and Commit}\\Manual data validation followed by bulk \texttt{UPSERT} to Supabase};

\draw[arrow] (step1) -- (step2);
\draw[arrow] (step2) -- (step3);
\draw[arrow] (step3) -- (step4);
\draw[arrow] (step4) -- (step5);

\end{tikzpicture}
\caption{Data Ingestion Pipeline for Excel Timetables}
\label{fig:parsing_pipeline}
\end{figure}

\begin{enumerate}
    \item \textbf{Binary Parsing:} Uses the \texttt{SheetJS} library to read `.xlsx` files and convert them into JSON arrays.
    \item \textbf{Header Synchronization:} Identifies time-slot boundaries from the header row, supporting various time formats and identifying merged cells for multi-hour sessions.
    \item \textbf{Metadata Extraction:} Uses Regular Expressions to identify subject codes, faculty names, and credit structures. It handles complex strings such as split-section assignments.
    \item \textbf{Grid Traversal:} Maps grid cells to specific days and times, extracting room and section information.
    \item \textbf{Review and Commit:} Provides an interface for manual correction before performing bulk \texttt{UPSERT} operations to Supabase.
\end{enumerate}

%-----------------------------------
The application uses state-based view management rather than traditional URL routing. A central `currentView` state in the root component determines the active module.
\begin{itemize}
    \item \texttt{import}: Mounts the \texttt{TimetableImporter}.
    \item \texttt{generator}: Mounts the multi-step \texttt{GeneratorView} wizard for automated timetable creation.
    \item \texttt{editor}: Mounts the interactive \texttt{EditorView} for drag-and-drop timetable refinement with LNS auto-fix.
    \item \texttt{student}: Mounts the \texttt{TimetableViewer} (All Students administrative view).
    \item \texttt{prof}: Mounts the \texttt{ProfessorTimetableViewer}.
    \item \texttt{room}: Mounts the \texttt{RoomTimetableViewer}.
    \item \texttt{master-room}: Mounts the campus-wide \texttt{MasterRoomViewer}.
    \item \texttt{free-room}: Mounts the \texttt{FreeRoomViewer}.
    \item \texttt{report-card}: Mounts the \texttt{ReportCardView}.
\end{itemize}

This approach ensures that only the logic and data required for the active module are loaded. Custom hooks (\texttt{useGeneratorData}, \texttt{useEditorData}) manage data fetching and caching, separating the data layer from the UI components.
